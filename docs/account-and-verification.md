# Аккаунт, компания и сценарий ЕСИА

## Что подключено фактически

- Вход MAX проверяется сервером по подписи исходного `WebAppData`. ID, переданный отдельно клиентом, не используется для авторизации.
- `/api/account` создаёт постоянный UUID аккаунта, связанный с проверенным MAX ID. Компания хранится в SQLite на сервере; на другом устройстве её можно загрузить через «Мой бизнес → Настройки».
- Сохранение компании использует ревизию: одновременное изменение с другого устройства возвращает 409, а не перезаписывает сведения молча.
- Удаление компании очищает серверный профиль, подписку, оценки и очередь уведомлений. Аккаунт остаётся. Локальные черновики отделяются от удалённой компании.
- Публичные реквизиты загружаются по ИНН. Ручной ввод остаётся запасным способом. Неизвестные финансовые показатели остаются неизвестными.
- Исходный логотип: `main_logo.png`. В приложении используется уменьшенный `miniapp/src/business/main-logo.webp`.

## ЕСИА: граница реализации

Доступа к ЕСИА нет. По явному запросу владельца продукта пользовательский интерфейс показывает единый обычный путь без отметок «демо»: вход, согласие, выбор роли, подтверждение компании, подготовка и отправка заявки.

**Этот путь сейчас является имитацией. Он не подтверждает личность или реальные полномочия и ничего не отправляет в Госуслуги либо ведомства.** Пароли и сертификаты Госуслуг приложение не запрашивает. Надпись «Заявка принята» означает запись локальной квитанции симулятором.

Технически состояние отделено от реального аккаунта: `opora.esia-demo.v1`, модуль `verification-demo.ts`, квитанции с `mode: demo`. Значения не передаются на сервер как доказательство полномочий. Сервер всегда возвращает `authority: unverified`, `esia: not_configured`, `canSubmitApplications: false`; поддельные поля подтверждения из клиента игнорируются. Серверный `/verification/esia` возвращает 503 до подключения настоящего провайдера.

Смена ИНН сбрасывает подтверждение. Отправка требует входа, роли для выбранного ИНН, заполненного проекта, отметок всех известных документов и подтверждения комплекта. Повторный клик возвращает ту же квитанцию. Отключение Госуслуг в настройках очищает состояние симулятора. Ошибка отправки может воспроизводиться в тестах через `failSubmission`; отдельного пользовательского переключателя нет.

## Будущая настоящая интеграция

1. Оформить доступ организации и информационной системы к ЕСИА, получить параметры тестовой и промышленной интеграции.
2. Заменить локальный вход серверным адаптером: начало авторизации, защищённый callback, проверка ответа провайдера, привязка личности к аккаунту. Секреты и ключи хранить только на сервере.
3. Проверять полномочия по конкретному ИНН и их срок действия; выбор роли в интерфейсе не является доказательством.
4. Подключить отдельный адаптер подачи каждого оператора программы. Авторизация ЕСИА сама по себе не создаёт интеграцию отправки заявок.
5. Получать квитанции и статусы от оператора, хранить их серверно, обеспечить идемпотентность, аудит и повтор после сбоев. Не переносить локальные имитированные подтверждения в реальные.

## Проверено локально 26.09.2026

- API: 123 теста; интерфейсная логика: 55; production-сервер: 4. Все прошли.
- Браузер Chromium, 393×810 тёмная и 320×810 светлая темы: ручное добавление, уведомление о добавлении, отсутствие повторного поздравления при редактировании, отмена удаления, сохранение профиля при ошибке сервера, удаление и перезагрузка.
- Автозагрузка по ИНН с контролируемым ответом источника: основная кнопка, закрытые заполненные реквизиты, дополнительные параметры, сохранение описания деятельности на сервере.
- Аккаунт: второй браузер восстанавливает компанию; пустой новый клиент не отключает существующую подписку; чужой MAX ID не получает профиль; конфликт ревизий не затирает данные.
- Имитация ЕСИА: согласие обязательно, отсутствие полномочий блокирует подачу, представитель проходит проверку, неполный комплект блокируется, ошибка отправки сохраняет черновик, повтор создаёт квитанцию, квитанция сохраняется при перезагрузке, дубля нет.
- Реальная ЕСИА и фактическая отправка заявки не тестировались: интеграций нет. Отправка сообщения реальному пользователю MAX не производилась этими тестами.

Проверку токена бота (`GET /me`), источника мер и GigaChat выполняет deploy smoke-check. Ошибка модели не должна скрывать результат независимой проверки MAX. Секретные значения в журнал не выводятся.

Для production добавьте `BOT_TOKEN` в GitHub Actions Secrets. Деплой передаёт его по SSH в `/opt/app/.env.bot` с правами 600; API и бот читают один файл. Если токена нет, API возвращает `MAX_NOT_CONFIGURED`, а не ошибку пользовательской авторизации. Без токена невозможно проверить вход MAX или доставку сообщений.
