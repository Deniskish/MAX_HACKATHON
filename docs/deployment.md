# Публикация на сервер

Workflow `Deploy` запускается при push в main и вручную через Actions. Очередь общая для production; дополнительный `flock` на сервере не допускает одновременного переключения версий. Публикуется SHA запуска, а не подвижная вершина main. Устаревший запуск пропускается, если сервер уже содержит более новый коммит.

1. Исходники выбранного коммита распаковываются в отдельную приватную папку `/opt/opora-deploy/release-*`.
2. Там устанавливаются зависимости, запускаются тесты и собираются интерфейс, API и бот. До завершения этих шагов работающая версия не меняется.
3. Старые сборки и зависимости временно сохраняются, новые переносятся в `/opt/app`. Старые файлы с хешами в URL остаются доступными открытым вкладкам.
4. Перезапускаются процессы PM2. Проверяются API, frontend, сжатие, изображения, соответствие SHA интерфейса и API, устойчивость процессов. Только после этого сохраняется PM2-конфигурация.
5. При ошибке переключения или проверки возвращаются прежние исходники, сборки и зависимости; повторно проверяется предыдущая версия. Сбой отката явно завершает workflow с ошибкой.
6. Проверка публичного HTTPS выполняется отдельно с GitHub runner. Проблема внешнего ingress делает деплой красным, но не запускает слепой откат уже проверенного приложения.

Данные компаний, SQLite, каталоги, сертификаты и `.env` не перемещаются и не удаляются. Секреты передаются по SSH через stdin и хранятся с правами 600. При неудачном переключении приватная папка резервной копии остаётся для диагностики; её `pm2.json` содержит секреты и не должен попадать в логи или артефакты Actions.

Проверки DaData, GigaChat, авторизации MAX и источника Минфина выполняются отдельными шагами. Их сбои видны в предупреждениях и таблице результатов workflow; успешная установка приложения **не означает** доступность всех внешних сервисов. Проверка MAX не отправляет сообщения пользователям.

Ограничения: во время перезапуска PM2 возможен короткий перерыв. Это не схема безостановочного blue/green-деплоя. Автоматический откат обрабатывает ошибки команд и проверок, но не отключение сервера или SIGKILL; после такого прерывания нужны проверка `/opt/app`, приватной резервной копии и ручное восстановление. Изменения схемы БД должны оставаться совместимыми с предыдущей версией: откат кода не откатывает пользовательские данные.

Проверка установленной версии: `/version.json` и `/api/health` возвращают один SHA, без кеширования. При ручном восстановлении сначала остановите выполняющийся deployment, затем восстановите сохранённые каталоги и коммит из `backup/revision`, перезапустите PM2 с прежним окружением и выполните `npm run check:production --prefix miniapp`.
